## Задача 1. Сервис «Моя лента»

### 1.1. Архитектура и схема данных

**Главное решение — гибридный fan-out.** Авторов и категорий с небольшим числом подписчиков раскладываю в ленты при публикации (push). Источники с подписчиками выше порога (для начала 10 000) не раскладываю, их посты подмешиваю при чтении (pull). Лента пользователя — слияние двух частей. Иначе один пост автора-миллионника превращается в миллион записей, а если делать только pull, каждое открытие ленты собирает её из сотен источников.

**Компоненты**

| Компонент | Роль |
|---|---|
| FastAPI, несколько реплик за балансировщиком | API публикации, подписок, выдачи ленты. Без состояния |
| PostgreSQL | Источник правды: пользователи, посты, категории, подписки, outbox |
| Redis Cluster, шардинг по user_id | Материализованные ленты, таймлайны авторов и категорий, кэш карточек постов, счётчики |
| Kafka (на старте хватит Redis Streams) | События публикации и подписки, партиция по author_id |
| Fan-out воркеры на Python | Читают события, раскладывают post_id по лентам |
| S3-совместимое хранилище + CDN, воркер транскодинга | Медиа не проходит через FastAPI: загрузка по presigned URL, отдача с CDN |

**PostgreSQL**

```sql
users(id PK, handle, ...)

posts(id PK, author_id FK, created_at timestamptz, status, media_key, ...)
  INDEX (author_id, created_at DESC)

categories(id PK, slug, subscribers_count)

post_categories(post_id FK, category_id FK, PK(post_id, category_id))
  INDEX (category_id, post_id DESC)              -- таймлайн категории для pull

subscriptions(
  user_id FK, target_type smallint,              -- 1 автор, 2 категория
  target_id bigint, created_at,
  PK (user_id, target_type, target_id))
  INDEX (target_type, target_id, user_id)        -- «кто подписан» для fan-out

outbox(id PK, event_type, payload jsonb, created_at, published_at NULL)
```

Id постов — ULID: генерируется без обращения к базе, сортируется по времени и не выдаёт общее число постов.

**Redis**

```
feed:{user_id}         ZSET  score = created_at мс, member = post_id   cap 1000, TTL 30 дней без чтения
tl:author:{id}         ZSET  последние ~500 постов автора
tl:cat:{id}            ZSET  последние ~500 постов категории
hot:authors, hot:cats  SET   источники в режиме pull
subs:{user_id}         SET   "a:123", "c:7" — кэш подписок
post:{id}              HASH  карточка поста, TTL
```

ZSET выбран из-за двух свойств. Score по времени даёт хронологию и курсор. Member = post_id даёт дедупликацию: пост, пришедший через автора и через две его категории, лежит в ленте один раз. Без этого дубли пришлось бы вычищать на чтении.

### 1.2. Механика

**Публикация поста**

1. Клиент заливает медиа в S3 по presigned URL. Транскодинг — отдельный воркер, пост становится `ready` по его завершении.
2. `POST /posts`. В одной транзакции: запись в `posts`, `post_categories` и событие в `outbox`. Ответ 201 сразу, в запросе ничего тяжёлого.
3. Outbox-relay публикует `post.published {post_id, author_id, category_ids, created_at}` в Kafka с ключом author_id. Так событие не теряется, если сервис упал между коммитом и отправкой в брокер.
4. Fan-out воркер:
   - Добавляет post_id в таймлайн автора и каждой из его категорий (`ZADD`). Это нужно и для pull, и для бэкфилла новым подписчикам.
   - Для каждого источника не из `hot:*` выбирает подписчиков из `subscriptions` пачками по 1 000 по id (не через OFFSET), собирает id в множество (один пользователь мог быть подписан и на автора, и на категорию), одним пакетом команд добавляет post_id в ленту каждого, обрезает ленту до 1 000 записей и продлевает TTL.
   - Горячие источники пропускает.
   - Повторная обработка события даёт тот же результат, поэтому ретраи воркера безопасны.
5. Редактирование — инвалидация `post:{id}`. Удаление — tombstone в карточке, фильтр при чтении, фоновая чистка таймлайнов.

**Запрос ленты** `GET /feed?cursor=<ts>_<post_id>&limit=20`

1. Push-часть: из `feed:{uid}` берём записи старше курсора, от новых к старым, `limit + запас`.
2. Pull-часть: пересечение `subs:{uid}` с `hot:*`. У обычного пользователя это от нуля до пары десятков источников. По каждому читаем его таймлайн от того же курсора. Все команды к Redis уходят одним пакетом.
3. Слияние по score, дедупликация по post_id, отсечение по `limit`. Следующий курсор — пара (score, post_id) последнего элемента, потому что времена могут совпасть.
4. Карточки: одним запросом из `post:{id}`, промахи одним `SELECT ... WHERE id IN (...)` с прогревом кэша. Фильтр удалённых и заблокированных. Медиа — ссылки на CDN.
5. Ленты нет в Redis (новый пользователь, долго не заходил, Redis потеряли): rebuild из Postgres по подпискам за 30 дней, до 1 000 записей, под блокировкой на пользователя (ключ в Redis с условием «только если не существует»), чтобы параллельные запросы не строили одно и то же. Пустая лента и отсутствующая различаются маркером.

Где что лежит: подписки — в Postgres, с кэшем в `subs:{uid}`. Готовые ленты — в Redis и восстанавливаются из Postgres. Redis можно потерять целиком без потери данных, только с нагрузкой на rebuild.

**Подписка на автора или категорию**

1. `INSERT ... ON CONFLICT DO NOTHING` в `subscriptions`. Счётчик подписчиков в Redis, периодический сброс в Postgres, чтобы строка популярного автора не стала точкой конкуренции.
2. Добавить источник в `subs:{uid}`.
3. Источник не горячий — бэкфилл: последние 50 постов из `tl:*` в `feed:{uid}` тем же запросом. Дёшево, и подписка видна сразу.
4. Источник горячий — ничего, pull подхватит при следующем чтении.
5. Отписка: удаление строки и источника из `subs:{uid}`. Из ленты сразу не вычищаю, при чтении фильтрую по `subs:{uid}`, чистку делаю фоном.
6. Источник перешёл порог: фоновая job добавляет его в `hot:*`, fan-out перестаёт пушить. Старые записи в лентах остаются, новые приходят через pull. Обратный переход — симметрично с бэкфиллом.

### 1.3. Узкие места и масштабирование

| Проблема при росте | Решение |
|---|---|
| Fan-out популярного автора: один пост — миллионы ZADD, лаг лент | Гибрид. Порог подбирается по лагу доставки p99. Партиции по author_id, воркеры масштабируются горизонтально |
| Память Redis: запись ZSET 60–80 байт, 1 000 постов на 10 млн активных ≈ 700 ГБ | Ленты только активным (TTL по последнему чтению, ленивый rebuild), cap на длину, шардинг |
| Пользователь с сотнями горячих подписок — дорогое слияние при чтении | Лимит источников в pull-части, остальные материализуются в его ленту фоновой job. Кэш первой страницы на 10–30 с |
| Горячие строки Postgres: счётчики, обратный поиск подписчиков в fan-out | Счётчики в Redis, реплики на чтение, партиционирование `subscriptions` по target |
| Массовый rebuild после потери Redis | Блокировка на пользователя, лимит одновременных rebuild, отдача неполной ленты |
| Порядок и дубли событий | Ключ Kafka = author_id, идемпотентный ZADD, outbox |
| Удалённые посты в готовых лентах | Tombstone при чтении карточки, фоновая очистка |
| Медиа | Отдельный пайплайн, CDN, не через API |
| Postgres как одна точка | Реплики для чтения карточек и rebuild. Шардинг по author_id только когда упрёмся |

Что сознательно не делаю на старте: ранжирование (в задаче хронология), мультирегион, перенос лент в Cassandra или ScyllaDB. Это следующий этап, когда метрики покажут предел. Метрики, за которыми слежу с первого дня: лаг доставки в ленту, hit ratio `post:*`, доля запросов с rebuild, память Redis по шардам, p99 `/feed`, consumer lag.

## Задача 2. Производительность публичных страниц

### 2.1. Стратегия кэширования

**Nginx и версия под каждый размер экрана**

Буквально так делать не стал бы. Nginx не знает размер экрана: User-Agent даёт класс устройства, а Client Hints (`Sec-CH-Viewport-Width`, `Sec-CH-DPR`) приходят только из Chromium и только после `Accept-CH`, то есть первый запрос всегда без них. Каждая новая размерность в ключе кэша умножает число вариантов и делит hit ratio. При 90% гостей hit ratio и есть ответ на требование «гости не создают нагрузку на бэкенд».

Схема:

1. Одна HTML-версия для всех устройств. Адаптивная вёрстка, картинки через `srcset` / `sizes` или `next/image`, видео — poster и lazy. Размер выбирает браузер, у которого есть реальный viewport и DPR. Nginx держит один объект на URL.
2. Ключ кэша `$scheme$host$uri$is_args$args` с нормализацией: utm-параметры отбрасываются через `map`, cookie не участвуют, `Accept-Encoding` нормализован. На гостевых маршрутах `proxy_ignore_headers Set-Cookie`.
3. Картинки — отдельно, по URL. Сервис ресайза или CDN принимает `?w=360|640|960|1280`, конечный набор ширин. Nginx кэширует каждый вариант, их мало.
4. Если классы устройств всё же нужны (десктоп с другим layout): максимум два-три класса через `map $http_user_agent $device_class`, класс в ключе кэша и в заголовке `X-Device-Class` для upstream. Не через `Vary: User-Agent`, на CDN это убивает кэш.
5. Гость и авторизованный получают одну и ту же SSR-страницу. Кнопка «Подписаться», свой аватар и прочая персонализация дорисовываются на клиенте запросом `/api/me`. Альтернатива `proxy_cache_bypass $cookie_session` проще, но тогда авторизованные бьют в бэкенд на каждой странице.
6. Защита в пик: `proxy_cache_lock` (одна сборка страницы на всех ожидающих), `proxy_cache_use_stale updating error timeout http_5xx` с `proxy_cache_background_update` (отдаём старое, обновляем фоном), TTL HTML 30–120 с, `/_next/static` — `immutable` на год. На стороне Next.js — ISR для публичных страниц с ревалидацией по событию (`revalidateTag` на редактирование поста).

```nginx
map $http_user_agent $device_class {
    default            "desktop";
    ~*(mobile|android) "mobile";
}
map $args $clean_args { ~^(.*?)(&?utm_[^&]*)+(.*)$ $1$3; default $args; }

proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=pages:200m max_size=20g inactive=7d use_temp_path=off;

location / {
    proxy_cache            pages;
    proxy_cache_key        "$scheme$host$uri$is_args$clean_args|$device_class";   # device_class — только если он нужен
    proxy_cache_valid      200 60s;
    proxy_cache_lock       on;
    proxy_cache_lock_timeout 2s;
    proxy_cache_use_stale  updating error timeout http_500 http_502 http_503 http_504;
    proxy_cache_background_update on;
    proxy_ignore_headers   Set-Cookie;
    proxy_hide_header      Set-Cookie;
    proxy_set_header       X-Device-Class $device_class;
    add_header             X-Cache-Status $upstream_cache_status;
    proxy_pass             http://nextjs;
}
location /_next/static/ { proxy_cache pages; proxy_cache_valid 200 365d; expires 1y; add_header Cache-Control "public, immutable"; proxy_pass http://nextjs; }
location /api/          { proxy_cache off; proxy_pass http://fastapi; }
```

Перед Nginx — CDN с теми же правилами, Nginx тогда второй уровень.

**Адаптация под железо на клиенте**

Страница одна, решение о тяжести интерфейса принимает клиент после загрузки. Так кэш остаётся целым.

Как определяю tier устройства. Один раз при загрузке, результат в `localStorage` и в `data-tier` на `<html>`:

- статика: `navigator.hardwareConcurrency`, `navigator.deviceMemory` (Chromium), `connection.effectiveType` и `saveData` (Chromium), `prefers-reduced-motion`, `prefers-reduced-data`;
- проба во время работы: были ли длинные задачи в главном потоке в первые секунды, время до первого рендера;
- заголовок `X-Device-Class` от сервера как подсказка, решение остаётся за клиентом.

Пример порогов: `low` — до 4 ядер, или `deviceMemory ≤ 2`, или `2g`, или `saveData`. `high` — от 8 ядер и `deviceMemory ≥ 4`. Остальное `mid`. Пороги уточняются по RUM.

Что переключается по tier:

| Область | low | mid / high |
|---|---|---|
| Анимации | Класс на `<html>` отключает transitions, parallax, blur. Автоплей видео → poster. Тяжёлые анимационные компоненты не монтируются | Полные |
| Списки | Виртуализация всегда. Меньший overscan, карточки без hover-эффектов и вторичных превью | Полные карточки |
| Бандл | Редактор комментариев, плеер, emoji-picker, share-sheet грузятся `next/dynamic` по намерению (tap или focus на зону), не по появлению. Модули жестов и предзагрузки не импортируются | Условный `import()` расширенных модулей |
| Сеть | `prefetch={false}` на `<Link>`, меньший cap DPR для картинок | Prefetch включён |
| Гидратация | Ниже fold — `Suspense` + lazy, монтирование по `IntersectionObserver` | Обычная |

Бандл один, два не собираю: разница в условных `import()`.

Чтобы не словить hydration mismatch: всё, что меняет DOM, применяется после монтирования. Всё, что можно сделать CSS-ом, делается через `data-tier`, который инлайн-скрипт в `<head>` выставляет до React. CSS-различия mismatch не вызывают.

Проверка: RUM с разбивкой по tier (INP, LCP, TBT, long tasks) и A/B на доле пользователей. Если облегчение убирает анимации, но INP не меняется, его откатываю.

### 2.2. Настройка таймаутов

Страница поста собирается из поста (без него страницы нет), профиля автора (нужен, но есть деградация) и комментариев (не нужны для первого экрана). Комментарии с p95 три секунды в критическом пути SSR держать нельзя: сервер ждёт за всех, а соединения Nginx и event loop Node общие. Поэтому комментарии получают короткий серверный бюджет и честный fallback: при промахе страница уходит без них и догружает их на клиенте, где ждать может браузер, а не сервер. В App Router это стриминг: shell уходит сразу, блок комментариев — свой `Suspense`.

**Уровни и значения.** Снаружи внутрь. Каждый внешний строго больше внутреннего с запасом на сеть и сериализацию.

| Уровень | Параметр | Значение | При срабатывании | Что видит пользователь |
|---|---|---|---|---|
| Nginx → Next.js | `proxy_connect_timeout` / `proxy_read_timeout` / `proxy_send_timeout` | 1 с / 5 с / 5 с | Гостям stale из кэша. Без кэша — статическая страница 504 с авторефрешем. `proxy_next_upstream error timeout`, 2 попытки, только GET | Чуть устаревшая, но целая страница |
| Next.js, бюджет рендера страницы | `AbortSignal.timeout` на критичные данные, стриминг | 3 с, shell за 500 мс | Срабатывать почти не должен. 500 → Nginx отдаёт stale | То же |
| Next.js, fetch поста | `AbortSignal.timeout(800)`, один ретрай на connect-ошибку | 800 мс | 503 → stale. Без кэша — страница ошибки | Stale или ошибка, поста без данных не бывает |
| Next.js, fetch профиля | | 500 мс | Шапка из данных поста: имя, без статистики | Пост читается, шапка упрощённая |
| Next.js, fetch комментариев | | 1 000 мс | Плейсхолдер и клиентский запрос с бюджетом 5–8 с | «Комментарии загружаются», потом либо комментарии, либо «не удалось, обновить» |
| FastAPI, хендлер `/comments` | Дедлайн из заголовка `X-Deadline-Ms`, иначе 900 мс | 900 мс | 504, учёт в circuit breaker | |
| FastAPI → сервис комментариев, httpx | `Timeout(connect=0.2, read=0.6, write=0.3, pool=0.2)`, `Limits(max_connections=100)` | ≈ 0,8 с | Исключение → 504 наружу. Пул ограничен: медленные комментарии не съедают все соединения | |
| Circuit breaker на комментарии | 50% ошибок за 10 с → open на 30 с, half-open одним запросом | | В open мгновенный 503 с `Retry-After`, сервис не трогаем | Плейсхолдер сразу, а не через секунду |

```python
client = httpx.AsyncClient(
    timeout=httpx.Timeout(connect=0.2, read=0.6, write=0.3, pool=0.2),
    limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
    transport=httpx.AsyncHTTPTransport(retries=0),   # ретраи явно, не неявно
)
```

```ts
const comments = fetch(`${API}/posts/${id}/comments`, {
  signal: AbortSignal.timeout(1000),
  headers: { "X-Deadline-Ms": "900" },
  next: { revalidate: 30 },
}).catch(() => null);   // null → <CommentsFallback />, догрузка на клиенте
```

**Почему бюджет убывает внутрь.** Если внутренний таймаут длиннее внешнего, внешний уровень уже отдал ошибку или stale, а внутренний продолжает работать для клиента, которого нет. Ресурс сжигается, деградация усиливается, наружу уходит безликий 504 вместо своего fallback. Каждый уровень должен падать первым там, где его fallback дешевле всего: комментарии — в Next, где есть плейсхолдер; пост — в Nginx, где есть stale. Запас между уровнями (0,8 → 0,9 → 1 → 3 → 5) покрывает сеть, очередь event loop и сериализацию. Дедлайн в заголовке позволяет FastAPI не начинать работу, на которую уже нет времени.

**Ретраи к сервису комментариев**

Автоматических ретраев по таймауту нет. Таймаут означает, что сервис уже не успевает. Повтор удваивает нагрузку в тот момент, когда он захлёбывается, поднимает его p95 ещё выше и тянет за собой FastAPI (занятые соединения) и Next (ожидание). Это основной случай, когда ретраи опасны.

Допустим один ретрай на ошибку соединения до отправки запроса: connection refused, reset, протухший keepalive. Это смена инстанса, а не нагрузка на деградирующий сервис. С джиттером, только GET, с бюджетом ретраев до 10% трафика, никогда при открытом breaker.

Ещё опасны: ретраи POST без idempotency-key (двойная подписка), ретраи на каждом уровне (Nginx × Next × FastAPI = восемь попыток вместо одной), ретраи без общего дедлайна.

Правильное место для повтора — клиент после загрузки страницы. Он размазан во времени, виден пользователю и отключается флагом.

**Метрики**

- TTFB и p95/p99 рендера страницы поста не растут, когда растёт p95 комментариев. Смотреть два графика рядом: это и есть проверка, что комментарии вышли из критического пути.
- Доля страниц без комментариев (fallback rate) и доля, где комментарии потом догрузились на клиенте. В пик fallback ожидаем, в норме около нуля. Алерт, если fallback держится вне пика: деградация стала нормой.
- Таймауты по уровням: httpx timeout rate, Next fetch abort rate по источнику, Nginx 504/499/502, гистограмма `upstream_response_time` против бюджета.
- Breaker: время в open за сутки. Retry ratio. Ожидания `pool` в httpx — признак давления на bulkhead.
- `$upstream_cache_status`: доля HIT, STALE, UPDATING. Рост STALE в пик означает, что схема работает.
- Ресурсы: event loop lag в Node, занятые воркеры FastAPI, открытые соединения к сервису комментариев (должны упираться в лимит, не расти).
- RUM: через сколько секунд комментарии видны, INP на странице.

### 2.3. Кнопка подписки и бюджетные устройства

**Что происходит 5–7 секунд.** SSR отдаёт готовый HTML, браузер рисует кнопку почти сразу, LCP хороший. Обработчик клика появляется только после гидратации. Для неё нужно скачать JS (бюджетный смартфон, средний мобильный канал), распарсить и скомпилировать (CPU в 4–6 раз медленнее десктопа), выполнить, а потом React проходит всё дерево и сверяет его с DOM. Без границ `Suspense` гидратация идёт целиком: пока React не обработал плеер и ветку комментариев, до кнопки он не дошёл. Главный поток занят long tasks: гидратация, аналитика, сторонние скрипты. Клики в это время не обрабатываются и не ставятся в очередь, перехватить их некому. Часто добавляется ещё один round-trip: кнопка узнаёт своё состояние через `useEffect` → `/api/me` и до ответа либо disabled, либо игнорирует клик. Итог: видна сразу, живая через TTI, а TTI на таких устройствах и есть 5–7 с. Бандл уже оптимизирован, значит основная цена — CPU на гидратацию дерева, и уменьшение байтов её почти не меняет.

**Подходы**

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| 1. Прогрессивное улучшение: `<form method="post">` + Server Action | Кнопка — нативный submit, работает без JS с первой отрисовки. После гидратации тот же компонент получает optimistic UI | Работает всегда и везде. Минимум кода, штатно в App Router. Вызов FastAPI с сервера | До гидратации клик — полная навигация (POST → redirect → GET), потеря скролла, мигание. Нужна CSRF-защита и идемпотентность |
| 2. Границы `Suspense`, selective hydration | Плеер, комментарии, рекомендации в `Suspense` + lazy. React гидратирует блок, по которому кликнули, первым и воспроизводит клик | Без изменения архитектуры. Ускоряет всё, не только кнопку | Сначала нужно скачать и запустить React и chunk страницы. На слабых устройствах всё ещё 2–3 с. Требует дисциплины с границами |
| 3. Инлайн-перехват и replay | Скрипт в `<head>` ловит клики по `[data-action]`, показывает pending, React доигрывает после гидратации | Мгновенная обратная связь, маленький | Самодельная сложность, дублирование логики, риск двойной отправки |
| 4. Кнопка как отдельный остров | Мини-бандл на 5 КБ (vanilla или Preact) с высоким приоритетом, живёт до основного React | Интерактивна почти сразу | Два мира: синхронизация состояния с React после гидратации, усложнение сборки |
| 5. Больше Server Components | Неинтерактивное в RSC, клиентское дерево меньше | Снижает цену гидратации | Судя по условию, частично сделано. Эффект постепенный |
| 6. Disabled или skeleton до гидратации | Честно показать, что кнопка ещё не готова | Дёшево | Кнопка всё равно неживая 5–7 с |

**Что внедрил бы у нас: первый подход как основу, второй вместе с ним.**

Почему. Аудитория на 90% гости, авторизованных с кнопкой меньшинство, но именно они конвертируют в подписку, и заметная их часть на бюджетных устройствах. Форма с Server Action делает кнопку рабочей в момент отрисовки HTML без единого байта JS. Стек уже App Router, запрос в FastAPI идёт с сервера: без CORS, cookie пробрасываются, можно добавить дедлайн. После гидратации тот же компонент получает `useOptimistic` и работает без перезагрузки, опыт на флагманах не ухудшается. Границы `Suspense` вокруг плеера и комментариев сокращают время до гидратации самой кнопки, а клики между загрузкой React и гидратацией React воспроизводит сам. Оба механизма штатные, поэтому третий и четвёртый подходы с их самодельным replay и вторым рантаймом не нужны.

Сразу добавил бы: pending-состояние кнопки на чистом CSS, без JS, идемпотентный `POST /subscribe` в FastAPI через `ON CONFLICT DO NOTHING` (двойной клик безопасен), RUM-счётчик кликов до гидратации по флагу `window.__hydrated`, чтобы видеть эффект в цифрах.

**Минусы, которые останутся жить**

- До гидратации клик — полноценная навигация: POST, редирект, перерисовка, потеря скролла (смягчается якорем `#subscribe` в redirect), мерцание на слабом устройстве. Хуже SPA-опыта, лучше «ничего не происходит».
- В кэшированной гостевой странице кнопка всегда «Подписаться». Подписанный пользователь увидит «Вы подписаны» только после `/api/me` на клиенте. Короткое неверное состояние — цена одной версии страницы в кэше.
- Серверные экшены — нагрузка на Next-сервер ради меньшинства пользователей и привязка к механизму Next.js. При смене фреймворка эту часть переписывать.
- До гидратации нет optimistic UI. Обязательна защита от двойного submit и CSRF для форм без JS.
- Границы `Suspense` надо поддерживать. Один новый тяжёлый клиентский компонент вне границы вернёт проблему.

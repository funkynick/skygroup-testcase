## Задача 1. Сервис «Моя лента»

**Решение.** Гибридный fan-out: посты обычных авторов и категорий раскладываются по лентам подписчиков при публикации (push), посты источников с большой аудиторией подмешиваются при чтении (pull). Лента хранится в Redis как отсортированное множество, Postgres — источник правды, события идут через outbox и брокер.

**Почему.** Только push ломается на авторе с миллионом подписчиков: один пост — миллион записей. Только pull делает каждое открытие ленты сборкой из сотен источников. Гибрид оставляет чтение дешёвым для большинства и ограничивает цену публикации сверху.

**Компромисс.** Две ветки доставки, переход между ними и обязательная фильтрация на чтении. Лента в Redis — производная, её можно потерять и пересобрать, но пересборка стоит запросов к Postgres.

### 1.1. Архитектура и схема данных

| Компонент | Роль |
|---|---|
| FastAPI, несколько реплик за балансировщиком | API публикации, подписок, выдачи ленты. Без состояния |
| PostgreSQL | Источник правды: пользователи, посты, категории, подписки, счётчики, outbox |
| Redis Cluster | Материализованные ленты, таймлайны авторов и категорий, кэш карточек постов и подписок |
| Kafka (на старте хватит Redis Streams) | События публикации и подписки, партиция по author_id |
| Fan-out воркеры на Python | Читают события, раскладывают post_id по лентам |
| S3-совместимое хранилище + CDN, воркер транскодинга | Медиа не проходит через FastAPI: загрузка по presigned URL, отдача с CDN |

**PostgreSQL**

```sql
users(id PK, handle, ...)

posts(id PK, author_id FK, status,                -- processing | published | failed | deleted
      created_at, published_at NULL, media_key, ...)
  INDEX (author_id, published_at DESC) WHERE status = 'published'

categories(id PK, slug, subscribers_count)
authors_stats(author_id PK, subscribers_count, mode)   -- mode: push | pull

post_categories(post_id FK, category_id FK, PK(post_id, category_id))
  INDEX (category_id, post_id DESC)

subscriptions(
  user_id FK, target_type smallint,              -- 1 автор, 2 категория
  target_id bigint, created_at,
  PK (user_id, target_type, target_id))
  INDEX (target_type, target_id, user_id)        -- «кто подписан» для fan-out

outbox(id PK, event_type, payload jsonb, created_at, published_at NULL)
```

Id постов — ULID: генерируется без обращения к базе, сортируется по времени и не выдаёт общее число постов.

**Redis**

```
feed:{uid}        ZSET  score = published_at мс, member = post_id   cap 1000, TTL 30 дней с последнего чтения
subs:{uid}        SET   "a:123", "c:7", "-"   — полная копия подписок, "-" = маркер «загружено»
tl:author:{id}    ZSET  последние ~500 опубликованных постов автора
tl:cat:{id}       ZSET  последние ~500 постов категории
hot:authors       SET   id авторов в режиме pull
hot:cats          SET   id категорий в режиме pull
post:{id}         HASH  карточка: author_id, category_ids, статус, медиа. TTL
```

Фигурные скобки в `feed:{uid}` и `subs:{uid}` — hash tag: ключи одного пользователя лежат на одном узле кластера, их можно читать одним пакетом. `hot:*` — два небольших множества на весь кластер, проверка членства идёт одной командой `SMISMEMBER` со списком id. Таймлайны источников разбросаны по узлам, их читают параллельно, не одним пакетом.

ZSET выбран из-за двух свойств. Score по времени даёт хронологию и курсор. Member = post_id даёт дедупликацию: пост, пришедший через автора и через две его категории, лежит в ленте один раз.

### 1.2. Механика

**Публикация поста**

1. Клиент получает presigned URL и заливает медиа в S3. `POST /posts` сохраняет метаданные со статусом `processing`, отвечает 201 с этим статусом и ставит задачу транскодинга. В ленты пока ничего не уходит, по прямой ссылке пост виден только автору.
2. Воркер транскодинга делает версии медиа. Успех: в одной транзакции `status = published`, `published_at = now()` и событие `post.published` в `outbox`. Ошибка: `status = failed`, автор видит причину и может перезалить. Событие публикации не создаётся, пока обработка не завершилась успехом.
3. Outbox-relay отправляет `post.published {post_id, author_id, category_ids, published_at}` в Kafka с ключом author_id. Доставка at-least-once: событие может прийти дважды, обработка ниже это переживает.
4. Fan-out воркер:
   - Добавляет post_id в таймлайн автора и каждой категории (`ZADD`).
   - Читает режим источников (`mode` автора, членство категорий в `hot:cats`) в момент обработки. Для источников в режиме push выбирает подписчиков из `subscriptions` пачками по 1 000 по id (не через OFFSET), собирает id в множество (один пользователь мог быть подписан и на автора, и на категорию), и добавляет post_id в ленту каждого. Запись идёт через Lua-скрипт «добавить, только если лента существует, и обрезать до 1 000»: ленты неактивных пользователей не создаются, они соберутся при следующем чтении.
   - Для источников в режиме pull ничего не делает.
   - Повтор события даёт тот же результат, ретраи воркера безопасны.
5. Редактирование — инвалидация `post:{id}`. Удаление или блокировка — `status = deleted`, tombstone в карточке, фильтр при чтении, фоновая чистка таймлайнов.

**Запрос ленты** `GET /feed?cursor=<score>_<post_id>&limit=20`

1. Push-часть: из `feed:{uid}` берём записи со score не больше курсора, от новых к старым, `limit + запас`. Записи с тем же score, что у курсора, и member не меньше его member отбрасываем в коде: так два поста в одну миллисекунду листаются ровно один раз. При равном score ZSET сортирует по member, ULID растёт по времени, порядок стабилен.
2. Pull-часть: список подписок из `subs:{uid}` (при промахе — из Postgres с записью в кэш). Два запроса `SMISMEMBER hot:authors` и `SMISMEMBER hot:cats` по id из подписок дают список горячих источников. У обычного пользователя их от нуля до пары десятков. По каждому читаем таймлайн от того же курсора, запросы параллельно.
3. Слияние по score, дедупликация по post_id, отсечение по `limit`. Следующий курсор — пара (score, post_id) последнего элемента. Новый пост, опубликованный во время листания, сдвинет границу первой страницы, для живой хронологической ленты это нормально.
4. Карточки: одним запросом из `post:{id}`, промахи одним `SELECT ... WHERE id IN (...)` с прогревом кэша. Дальше фильтр актуальности по карточке: пост остаётся, если текущие подписки содержат его автора или хотя бы одну из его категорий. Это закрывает отписку и гонку с fan-out, который мог дописать пост после отписки. Удалённые и заблокированные отбрасываются по tombstone. Медиа — ссылки на CDN.
5. Ленты нет в Redis (новый пользователь, долго не заходил, Redis потеряли): rebuild из Postgres по подпискам за 30 дней, до 1 000 записей, под блокировкой на пользователя (ключ с условием «только если не существует»), чтобы параллельные запросы не строили одно и то же. Пустая лента и отсутствующая различаются маркером. Чтение продлевает TTL ленты.

Где что лежит: подписки — в Postgres, с полной копией в `subs:{uid}`. Готовые ленты — в Redis и восстанавливаются из Postgres. Redis можно потерять целиком без потери данных, только с нагрузкой на rebuild.

**Подписка на автора или категорию**

1. `INSERT ... ON CONFLICT DO NOTHING` в `subscriptions`. Счётчик подписчиков увеличивается в той же транзакции и только если строка реально вставлена (по rowcount). Повторная подписка счётчик не трогает.
2. После коммита — `DEL subs:{uid}`. Кэш подписок не дописывается по одной записи, а инвалидируется и при следующем чтении загружается целиком с маркером «загружено». Кэш либо полный, либо отсутствует, «ложно полного» состояния нет. Redis недоступен — читаем подписки из Postgres напрямую, лента медленнее, но корректна.
3. Источник в режиме push — бэкфилл: последние 50 постов из его таймлайна в `feed:{uid}` тем же Lua-скриптом. Подписка видна сразу.
4. Источник в режиме pull — ничего, pull подхватит при следующем чтении.
5. Отписка: `DELETE` и счётчик только при реально удалённой строке, `DEL subs:{uid}`. Из ленты сразу не вычищаю: фильтр на чтении (шаг 4 выше) скрывает пост, если ни одна из оставшихся подписок к нему не подходит, и оставляет, если подходит хотя бы одна. Фоновая чистка применяет то же правило.
6. Переход источника между режимами. Правило: новый путь включается раньше, чем выключается старый. Push → pull: сначала источник добавляется в `hot:*` (pull начинает покрывать), fan-out продолжает push ещё окно, равное максимальному лагу доставки (например, 5 минут), потом `mode = pull`. Pull → push: сначала `mode = push` (fan-out начинает раскладывать), через то же окно источник убирается из `hot:*`. В окне перекрытия пост приходит двумя путями, `ZADD` дедуплицирует. В любой момент активен хотя бы один путь, потери на границе нет.

### 1.3. Узкие места и масштабирование

| Проблема при росте | Решение |
|---|---|
| Fan-out популярного автора: один пост — миллионы записей, лаг лент | Гибрид. Порог режима подбирается по лагу доставки p99. Партиции по author_id, воркеры масштабируются горизонтально |
| Память Redis. Грубая прикидка: 60–80 байт на запись, 1 000 постов на 10 млн активных ≈ 700 ГБ без реплик и служебных структур | Ленты только активным: TTL продлевается чтением, push не создаёт отсутствующую ленту. Cap на длину, шардинг. Точный sizing — после замера на реальных данных |
| Пользователь с сотнями горячих подписок — дорогое слияние при чтении | Лимит источников в pull-части, остальные материализуются в его ленту фоновой job. Кэш первой страницы на 10–30 с |
| Горячие строки Postgres: счётчики популярных авторов, обратный поиск подписчиков | Счётчики горячих авторов переносятся в Redis с периодическим сбросом, реплики на чтение, партиционирование `subscriptions` по target |
| Массовый rebuild после потери Redis | Блокировка на пользователя, лимит одновременных rebuild, отдача неполной ленты |
| Порядок и дубли событий | Ключ Kafka = author_id, идемпотентный ZADD, outbox |
| Удалённые посты в готовых лентах | Tombstone при чтении карточки, фоновая очистка |
| Медиа | Отдельный пайплайн, CDN, не через API |
| Postgres как одна точка | Реплики для чтения карточек и rebuild. Шардинг по author_id только когда упрёмся |

Что сознательно не делаю на старте: ранжирование (в задаче хронология), мультирегион, перенос лент в Cassandra или ScyllaDB. Это следующий этап, когда метрики покажут предел.

Чем калибрую допущения (порог 10 000 подписчиков, cap 1 000, бэкфилл 50, TTL 30 дней): p95 и p99 `/feed`, лаг доставки в ленту, доля запросов с rebuild, память Redis по шардам, hit ratio `post:*`, consumer lag.

## Задача 2. Производительность публичных страниц

**Решение.** Одна HTML-версия публичной страницы для всех устройств, закэшированная в CDN и Nginx без участия cookie. Адаптация под экран — браузером, под железо — клиентом после загрузки. Комментарии вне критического пути, с убывающими внутрь бюджетами времени. Кнопка подписки — обычная HTML-форма с Server Action, работает до загрузки JS.

**Почему.** При 90% гостей единственный способ снять нагрузку с бэкенда — высокий hit ratio, а его дают одинаковые ответы. Всё, что зависит от пользователя, вынесено из кэшируемого HTML. Деградация комментариев не должна тормозить пост, поэтому у них свой бюджет и свой fallback.

**Компромисс.** Авторизованные видят своё состояние (подписан, аватар) с задержкой после загрузки. Редактирование поста доживает TTL внешнего кэша. До гидратации клик по кнопке — полная перезагрузка страницы.

### 2.1. Стратегия кэширования

**Nginx и версия под каждый размер экрана**

Буквально так делать не стал бы. Nginx не знает размер экрана: User-Agent даёт класс устройства, а Client Hints (`Sec-CH-Viewport-Width`, `Sec-CH-DPR`) приходят только из Chromium и только после `Accept-CH`, то есть первый запрос всегда без них. Каждая новая размерность в ключе кэша умножает число вариантов и делит hit ratio.

Схема:

1. Маршруты делятся на два класса. Публичные: пост, профиль, видео. Только они кэшируются. Всё остальное (лента, настройки, `/api/*`, POST server actions) идёт мимо кэша всегда.
2. Инвариант: публичный HTML не зависит от cookie и Authorization. Nginx на публичных маршрутах не передаёт cookie upstream, поэтому Next.js физически не может персонализировать ответ. Если upstream всё же прислал `Set-Cookie` или `Cache-Control: private` / `no-store`, ответ не кэшируется. Кэшируются только GET и HEAD со статусом 200. Следствие: один пользователь не может получить данные другого из кэша, потому что в кэше нет ответов, построенных с учётом пользователя.
3. App Router отдаёт одну страницу в нескольких видах: HTML, RSC-payload для клиентской навигации (заголовок `RSC: 1`, параметр `_rsc` в query) и prefetch (`Next-Router-Prefetch`). Эти заголовки входят в ключ кэша, query не нормализуется, чтобы не потерять `_rsc`. `Vary` от Next.js пробрасывается как есть. Нормализация utm-параметров — отдельная задача после проверки, не часть базовой схемы.
4. Одна HTML-версия для всех устройств. Адаптивная вёрстка, картинки через `srcset` / `sizes` или `next/image`, видео — poster и lazy. Размер выбирает браузер. Картинки кэшируются по URL, набор ширин конечный (`?w=360|640|960|1280`).
5. Если классы устройств всё же нужны (десктоп с другим layout): максимум два-три класса через `map $http_user_agent $device_class`, класс в ключе кэша. Не через `Vary: User-Agent`, на CDN это убивает кэш.
6. Персонализация для авторизованных. Сессия в HttpOnly cookie, рядом отдельная cookie-маркер без токена (`li=1`), которую видит JS. Клиент вызывает `/api/me` только при наличии маркера. Гость на HIT не создаёт ни одного запроса к FastAPI.
7. Комментарии для гостей — отдельный публичный GET `/api/public/posts/{id}/comments?page=1`, без cookie, кэшируется в Nginx и CDN на 30–60 с, догружается при подходе к блоку. На HIT FastAPI не участвует. «Гости не создают нагрузку» здесь означает минимум динамических запросов к origin, не абсолютный ноль.
8. Защита в пик: `proxy_cache_lock` (одна сборка страницы на всех ожидающих), `proxy_cache_use_stale` на ошибках и таймаутах upstream, фоновое обновление. TTL берётся из `Cache-Control: s-maxage`, который Next.js ставит для ISR-страниц (revalidate 60 с).
9. Инвалидация. `revalidateTag` и `revalidatePath` чистят только кэш Next.js, внешний Nginx и CDN о них не знают. Базовый компромисс — короткий TTL: правка поста доживает до 60 с. Удаление и блокировка так ждать не могут: событие `post.deleted` вызывает purge по ключу в CDN (API) и в Nginx (удаление файла по хешу ключа или запрос с `proxy_cache_bypass`), а `404` кэшируется на 30 с, чтобы не бить в origin.

Проверка схемы: открыть страницу поста гостем, под пользователем А и под пользователем Б. HTML побайтно одинаковый, `X-Cache-Status: HIT` со второго запроса, в HTML нет имени, аватара и состояния кнопки. Запрос с `RSC: 1` возвращает RSC-payload, не HTML.

```nginx
# Псевдоконфигурация: показывает принципы, перед production проверить
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=pages:200m max_size=20g inactive=7d use_temp_path=off;

map $http_user_agent $device_class {
    default            "desktop";
    ~*(mobile|android) "mobile";
}

# Публичные страницы: пост, профиль, видео. Cookie до upstream не доходят
location ~ ^/(p|u|v)/ {
    proxy_set_header Cookie "";
    proxy_set_header Authorization "";
    proxy_cache            pages;
    proxy_cache_methods    GET HEAD;
    proxy_cache_key        "$scheme$host$request_uri|$http_rsc|$http_next_router_prefetch|$device_class";
    proxy_no_cache         $upstream_http_set_cookie;      # ответ с cookie в кэш не попадает
    proxy_cache_lock       on;
    proxy_cache_lock_timeout 2s;
    proxy_cache_use_stale  updating error timeout http_500 http_502 http_503 http_504;
    proxy_cache_background_update on;
    proxy_cache_valid      404 30s;                        # 200 — по s-maxage от Next.js
    add_header             X-Cache-Status $upstream_cache_status;
    proxy_pass             http://nextjs;
}
# Cache-Control и Vary от upstream не игнорируются: private / no-store не кэшируются

location /_next/static/ { proxy_cache pages; proxy_cache_valid 200 365d; expires 1y; add_header Cache-Control "public, immutable"; proxy_pass http://nextjs; }

# Комментарии для гостей
location /api/public/   { proxy_set_header Cookie ""; proxy_cache pages; proxy_cache_valid 200 30s; proxy_cache_lock on; proxy_pass http://fastapi; }

# Всё остальное — без кэша, с cookie
location /api/          { proxy_cache off; proxy_pass http://fastapi; }
location /               { proxy_cache off; proxy_pass http://nextjs; }
```

Перед Nginx — CDN с теми же правилами, Nginx тогда второй уровень.

**Адаптация под железо на клиенте**

Страница одна, решение о тяжести интерфейса принимает клиент после загрузки. Так кэш остаётся целым.

Как определяю tier устройства. Один раз при загрузке, результат в `localStorage` и в `data-tier` на `<html>`:

- сигналы браузера: `navigator.hardwareConcurrency`, `navigator.deviceMemory`, `connection.effectiveType` и `saveData`, `prefers-reduced-motion`. Все они неточные и есть не везде (`deviceMemory` и Network Information — только Chromium). Если сигнала нет, tier = `mid`, ничего не ломается;
- проба во время работы: были ли длинные задачи в главном потоке в первые секунды, время до первого рендера. Это точнее сигналов и может понизить tier;
- пороги уточняются по RUM: если устройства из `mid` показывают INP как `low`, порог двигается.

Пример стартовых порогов: `low` — до 4 ядер, или `deviceMemory ≤ 2`, или `2g`, или `saveData`. `high` — от 8 ядер и `deviceMemory ≥ 4`. Остальное `mid`.

Что переключается по tier:

| Область | low | mid / high |
|---|---|---|
| Анимации | Класс на `<html>` отключает transitions, parallax, blur. Автоплей видео → poster. Тяжёлые анимационные компоненты не монтируются | Полные |
| Списки | Виртуализация всегда. Меньший overscan, карточки без hover-эффектов и вторичных превью | Полные карточки |
| Бандл | Редактор комментариев, плеер, emoji-picker, share-sheet грузятся `next/dynamic` по намерению (tap или focus на зону), не по появлению. Модули жестов и предзагрузки не импортируются | Условный `import()` расширенных модулей |
| Сеть | `prefetch={false}` на `<Link>`, меньший cap DPR для картинок | Prefetch включён |
| Гидратация | Блоки ниже fold — отдельные компоненты в своих `Suspense`-границах, монтируются по появлению. Это надо проектировать на уровне компонентов, само по себе `Suspense` гидратацию не откладывает | Обычная |

Бандл один, два не собираю: разница в условных `import()`.

Чтобы не словить hydration mismatch: всё, что меняет DOM, применяется после монтирования. Всё, что можно сделать CSS-ом, делается через `data-tier`, который инлайн-скрипт в `<head>` выставляет до React. CSS-различия mismatch не вызывают.

Проверка: полевые метрики INP, LCP и long animation frames с разбивкой по tier, A/B на доле пользователей. TBT — лабораторная метрика, для сравнения сборок. Если облегчение убирает анимации, но INP не меняется, его откатываю.

### 2.2. Настройка таймаутов

Страница поста собирается из поста (без него страницы нет), профиля автора (нужен, но есть деградация) и комментариев (не нужны для первого экрана). Комментарии с p95 три секунды в критическом пути SSR держать нельзя: сервер ждёт за всех, а соединения Nginx и event loop Node общие.

Три пути, у каждого своё поведение:

- **Гость, кэш HIT.** Nginx или CDN отдаёт готовую страницу, Next.js и FastAPI не участвуют. Комментарии грузятся клиентом из кэшируемого endpoint (2.1, п. 7). Таймауты ниже этот путь не затрагивают.
- **Регенерация публичной страницы (MISS, истёк TTL).** Next.js рендерит страницу целиком и буферизованно: Nginx кэширует только полный ответ, стриминга здесь нет. В страницу входят пост и профиль с бюджетами из таблицы, комментарии в неё не входят. Если бюджет исчерпан до первого байта, Nginx отдаёт stale (если есть) или страницу ошибки.
- **Авторизованный пользователь или другая некэшируемая страница.** SSR со стримингом, на этом пути `proxy_buffering off` (и, как следствие, никакого Nginx-кэша, что и нужно). Shell уходит первым, цель 500 мс — это SLO, а не гарантия конфигурации. Блок комментариев — своя `Suspense`-граница с серверным бюджетом. После отправки заголовков заменить ответ на stale или 504 уже нельзя: при ошибке внутри границы Next.js отправляет чанк с ошибкой, и клиент показывает fallback этой границы; при обрыве стрима пользователь видит shell без блока комментариев, и клиентский код догружает их сам.

**Уровни и значения.** Снаружи внутрь. По цепочке передаётся не фиксированный таймаут, а оставшийся бюджет: каждый уровень вычитает свой запас и отдаёт остаток ниже.

| Уровень | Параметр | Значение | При срабатывании | Что видит пользователь |
|---|---|---|---|---|
| Nginx → Next.js | `proxy_connect_timeout` / `proxy_read_timeout` | 1 с / 10 с. `read_timeout` — пауза между двумя чтениями, не общее время ответа | До первого байта: `proxy_next_upstream error timeout`, 2 попытки, только GET, затем stale или страница 504. После первого байта: стрим обрывается | Stale или заглушка; при стриминге — shell без блока |
| Next.js, бюджет рендера | Дедлайн запроса в request-scope, каждому fetch передаётся остаток через `AbortSignal.timeout(remaining)` | 3 с на всё | Критичные данные не успели — 500, дальше Nginx | Stale или ошибка |
| Next.js, fetch поста | Параллельно с профилем | 800 мс, один ретрай на connect-ошибку | 503 → Nginx | Stale или ошибка, поста без данных не бывает |
| Next.js, fetch профиля | | 500 мс | Шапка из данных поста: имя, без статистики | Пост читается, шапка упрощённая |
| Next.js, fetch комментариев (только путь со стримингом) | `X-Deadline-Ms` = остаток, `response.ok` проверяется | min(1 000 мс, остаток) | Плейсхолдер, клиентская догрузка с бюджетом 5–8 с | «Комментарии загружаются», потом либо комментарии, либо «не удалось, обновить» |
| FastAPI, хендлер `/comments` | `asyncio.timeout(min(0.9, deadline − 0.1))` вокруг всего запроса | ≤ 900 мс | 504, учёт в circuit breaker, отмена httpx-запроса | |
| httpx → сервис комментариев | `Timeout(connect=0.2, read=0.6, write=0.3, pool=0.2)` — пофазные лимиты и паузы, не общий дедлайн. `Limits(max_connections=100)` | Каждая фаза отдельно, общий предел задаёт `asyncio.timeout` выше | Исключение → 504 наружу. Пул ограничен: медленные комментарии не съедают все соединения | |
| Circuit breaker на комментарии | 50% ошибок за 10 с → open на 30 с, half-open одним запросом | | В open мгновенный 503 с `Retry-After`, сервис не трогаем | Плейсхолдер сразу, а не через секунду |

`X-Deadline-Ms` — договорённость между Next.js и FastAPI: оставшиеся миллисекунды с точки зрения вызывающего, не timestamp. FastAPI вычитает запас 100 мс на сеть и сериализацию, берёт минимум со своим лимитом и проверяет, что остаток положительный. Отмена по `asyncio.timeout` закрывает соединение httpx и освобождает его в пуле. Сервис комментариев при этом может продолжать работу: удалённый запрос отменить нельзя. Поэтому ограничение сверху — пул соединений и breaker, а не только таймаут.

```python
client = httpx.AsyncClient(
    timeout=httpx.Timeout(connect=0.2, read=0.6, write=0.3, pool=0.2),  # лимиты фаз, не общий дедлайн
    limits=httpx.Limits(max_connections=100, max_keepalive_connections=20),
    transport=httpx.AsyncHTTPTransport(retries=0),                      # ретраи явно, не неявно
)

async def get_comments(post_id: str, deadline_ms: int | None) -> dict:
    budget = 0.9 if deadline_ms is None else min(0.9, (deadline_ms - 100) / 1000)
    if budget <= 0 or breaker.is_open():
        raise HTTPException(503, headers={"Retry-After": "30"})
    try:
        async with asyncio.timeout(budget):                 # общий дедлайн операции
            r = await client.get(f"{COMMENTS}/posts/{post_id}/comments")
            r.raise_for_status()
            return r.json()
    except (TimeoutError, httpx.HTTPError):
        breaker.record_failure()
        raise HTTPException(504)
```

```ts
async function loadComments(id: string, remainingMs: number) {
  const budget = Math.min(1000, remainingMs);
  try {
    const res = await fetch(`${API}/posts/${id}/comments`, {
      signal: AbortSignal.timeout(budget),
      headers: { "X-Deadline-Ms": String(budget) },
      cache: "no-store",
    });
    if (!res.ok) return null;        // 503 и 504 — тоже fallback, fetch сам не бросает
    return await res.json();
  } catch {
    return null;                     // таймаут и сетевые ошибки
  }
}
// null → <CommentsFallback />, догрузка на клиенте
```

**Почему бюджет убывает внутрь.** Если внутренний таймаут длиннее внешнего, внешний уровень уже отдал ошибку или stale, а внутренний продолжает работать для клиента, которого нет. Ресурс сжигается, деградация усиливается, наружу уходит безликий 504 вместо своего fallback. Каждый уровень должен падать первым там, где его fallback дешевле всего: комментарии — в Next.js, где есть плейсхолдер; пост — в Nginx, где есть stale. Запас между уровнями (0,6 на фазу → 0,9 → 1 → 3 → 10) покрывает сеть, очередь event loop и сериализацию.

**Ретраи к сервису комментариев**

Автоматических ретраев по таймауту нет. Таймаут означает, что сервис уже не успевает. Повтор удваивает нагрузку в тот момент, когда он захлёбывается, поднимает его p95 ещё выше и тянет за собой FastAPI (занятые соединения) и Next.js (ожидание). Это основной случай, когда ретраи опасны.

Допустим один ретрай на ошибку соединения до отправки запроса: connection refused, reset, протухший keepalive. Это смена инстанса, а не нагрузка на деградирующий сервис. С джиттером, только GET, с бюджетом ретраев до 10% трафика, в пределах оставшегося дедлайна, никогда при открытом breaker.

Ещё опасны: ретраи POST без idempotency-key (двойная подписка), ретраи на каждом уровне (Nginx × Next.js × FastAPI = восемь попыток вместо одной), ретраи без общего дедлайна.

Правильное место для повтора — клиент после загрузки страницы. Он размазан во времени, виден пользователю и отключается флагом.

**Метрики**

- TTFB и p95/p99 рендера страницы поста не растут, когда растёт p95 комментариев. Смотреть два графика рядом: это и есть проверка, что комментарии вышли из критического пути.
- Доля страниц без комментариев (fallback rate) и доля, где комментарии потом догрузились на клиенте. В пик fallback ожидаем, в норме около нуля. Алерт, если fallback держится вне пика: деградация стала нормой.
- Таймауты по уровням: срабатывания `asyncio.timeout` в FastAPI, abort по источнику в Next.js, Nginx 504/499/502, гистограмма `upstream_response_time` против бюджета.
- Breaker: время в open за сутки. Retry ratio. Ожидания `pool` в httpx — признак давления на bulkhead.
- `$upstream_cache_status`: доля HIT, STALE, UPDATING. Рост STALE в пик означает, что схема работает.
- Ресурсы: event loop lag в Node, занятые воркеры FastAPI, открытые соединения к сервису комментариев (должны упираться в лимит, не расти).
- RUM: через сколько секунд комментарии видны, INP на странице.

### 2.3. Кнопка подписки и бюджетные устройства

**Что происходит 5–7 секунд.** SSR отдаёт готовый HTML, браузер рисует кнопку почти сразу, LCP хороший. Обработчик клика появляется только после гидратации. Для неё нужно скачать JS (бюджетный смартфон, средний мобильный канал), распарсить и скомпилировать (CPU в 4–6 раз медленнее десктопа), выполнить, а потом React проходит дерево и сверяет его с DOM. Главный поток в это время занят длинными задачами: гидратация, аналитика, сторонние скрипты.

Клики в этом окне делятся на два случая. Пока рантайм React не загружен и не запущен, слушателей нет: клик теряется, перехватить его некому. Когда рантайм уже работает, но нужная часть дерева ещё не гидрирована, React может приоритизировать гидратацию `Suspense`-границы, в которую кликнули, и воспроизвести клик. Это работает только для дискретных событий внутри границ, которые для этого спроектированы, и только если код границы уже загружен; универсального «любой клик доиграется» нет. Без границ гидратация идёт целиком: пока React не обработал плеер и ветку комментариев, до кнопки он не дошёл.

Часто добавляется ещё один round-trip: кнопка узнаёт своё состояние через `useEffect` → `/api/me` и до ответа либо disabled, либо игнорирует клик. Итог: кнопка видна с первой отрисовки, а живой становится через окно, которое на таких устройствах и есть 5–7 с. Бандл уже оптимизирован, значит основная цена — CPU на гидратацию дерева, и уменьшение байтов её почти не меняет.

**Подходы**

| Подход | Суть | Плюсы | Минусы |
|---|---|---|---|
| 1. Прогрессивное улучшение: `<form action={serverAction}>` в Server Component | Кнопка — нативный submit, работает без JS с первой отрисовки. Client Component внутри формы добавляет pending и optimistic UI после гидратации | Работает всегда и везде. Минимум кода, штатно в App Router. Вызов FastAPI с сервера | До гидратации клик — полная навигация (POST → redirect → GET), потеря скролла, мигание. Нужны CSRF-защита, проверка авторизации и идемпотентность на сервере |
| 2. Границы `Suspense`, selective hydration | Плеер, комментарии, рекомендации в `Suspense` + lazy. React гидратирует блок, по которому кликнули, раньше остальных | Без изменения архитектуры. Ускоряет всё, не только кнопку | Нужен загруженный рантайм React и код границы. На слабых устройствах всё ещё 2–3 с. Требует дисциплины с границами |
| 3. Инлайн-перехват и replay | Скрипт в `<head>` ловит клики по `[data-action]`, показывает pending, React доигрывает после гидратации | Мгновенная обратная связь, маленький | Самодельная сложность, дублирование логики, риск двойной отправки |
| 4. Кнопка как отдельный остров | Мини-бандл на 5 КБ (vanilla или Preact) с высоким приоритетом, живёт до основного React | Интерактивна почти сразу | Два мира: синхронизация состояния с React после гидратации, усложнение сборки |
| 5. Больше Server Components | Неинтерактивное в RSC, клиентское дерево меньше | Снижает цену гидратации | Судя по условию, частично сделано. Эффект постепенный |
| 6. Disabled или skeleton до гидратации | Честно показать, что кнопка ещё не готова | Дёшево | Кнопка всё равно неживая 5–7 с |

**Что внедрил бы у нас: первый подход как основу, второй вместе с ним.**

Как устроено. Форма — Server Component: `<form action={subscribe}>`, где `subscribe` — серверная функция (`'use server'`). Next.js рендерит её как обычную HTML-форму со скрытым идентификатором действия, поэтому без JS браузер делает нативный POST, функция выполняется на сервере и делает `redirect()` обратно на профиль с якорем `#subscribe`. Внутри формы — Client Component `SubscribeButton` с `useFormStatus` для pending и `useOptimistic` для мгновенного «Вы подписаны». После гидратации он перехватывает submit, и перезагрузки нет. Это и есть граница Server/Client: форма и действие — серверные, состояние кнопки — клиентское, сценарий без JS от клиентской части не зависит.

На сервере функция `subscribe`: читает сессию из HttpOnly cookie, неавторизованного отправляет на вход с возвратом на профиль; проверяет, что target id существует и это не сам пользователь; вызывает `POST /subscribe` в FastAPI, который идемпотентен (`ON CONFLICT DO NOTHING`), поэтому двойной submit без JS даёт тот же результат, а не вторую подписку; затем `revalidatePath` профиля. CSRF: Next.js проверяет `Origin` против `Host` для server actions, cookie сессии — `SameSite=Lax`.

Почему это. Аудитория на 90% гости, авторизованных с кнопкой меньшинство, но именно они конвертируют в подписку, и заметная их часть на бюджетных устройствах. Форма делает кнопку рабочей в момент отрисовки HTML без единого байта JS. Стек уже App Router, запрос в FastAPI идёт с сервера: без CORS, cookie не покидают сервер, можно передать дедлайн. Опыт на флагманах не ухудшается. Границы `Suspense` вокруг плеера и комментариев сокращают окно до гидратации самой кнопки. Оба механизма штатные, поэтому третий и четвёртый подходы с их самодельным replay и вторым рантаймом не нужны.

Сразу добавил бы: pending-состояние кнопки на чистом CSS, без JS; RUM-счётчик кликов до гидратации по флагу `window.__hydrated` и полевые INP и long animation frames на странице профиля, чтобы видеть эффект в цифрах.

**Минусы, которые останутся жить**

- До гидратации клик — полноценная навигация: POST, редирект, перерисовка, потеря скролла (смягчается якорем `#subscribe` в redirect), мерцание на слабом устройстве. Хуже SPA-опыта, лучше «ничего не происходит».
- В кэшированной гостевой странице кнопка всегда «Подписаться». Подписанный пользователь увидит «Вы подписаны» только после `/api/me` на клиенте. Короткое неверное состояние — цена одной версии страницы в кэше.
- Серверные экшены — нагрузка на Next-сервер ради меньшинства пользователей и привязка к механизму Next.js. При смене фреймворка эту часть переписывать.
- До гидратации нет optimistic UI. Двойной submit без JS уходит на сервер дважды, его гасит идемпотентность бэкенда, а не клиент.
- Границы `Suspense` надо поддерживать. Один новый тяжёлый клиентский компонент вне границы вернёт проблему.
